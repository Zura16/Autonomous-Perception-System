# Decisions

Every non-obvious choice, why it was made, and what would break it. Append-only:
a decision that turns out wrong gets a **Superseded by** line, never a delete —
the reasoning that led somewhere wrong is worth more than the tidy final answer.

Format: `D-NNN · title · date · status`.

## D-001 · Claude writes the implementation, not the author · 2026-09-01 · Active

**Decision.** CLAUDE.md mandates coach mode (the author writes geometry, filters,
tracker association, and decision logic; Claude frames and reviews). On session
start the author explicitly chose the opposite: Claude writes everything, the
author reviews diffs.

**Why it is logged rather than silently followed.** The charter names the cost of
this exact choice — *"you end up unable to defend it in an interview, which is
the whole point of the project."* It was restated at the time of asking and the
choice was made anyway. That is the author's call to make; it is recorded here so
that neither party later mistakes reviewed code for written code.

**What this changes downstream.** `/quiz` becomes load-bearing rather than
optional, and the "interview version" closing line on every explanation is now
the primary transfer mechanism instead of a supplement. The four pieces the
charter singles out — monocular range geometry, the scale-rate/KF velocity
estimator, tracker association, FCW thresholds — should each get a `/warmup`-style
cold reimplementation before this project is put on a résumé.

**What would reverse it.** The author asking to take over any stage. Coach mode
resumes at that stage with no renegotiation.

## D-002 · Splits are by sequence, never by frame · 2026-09-01 · Active

**Decision.** `dev` / `val` / `test` are assigned per drive in
`configs/dataset.yaml`. No drive contributes frames to more than one split.

**Why.** KITTI frames arrive at ~10 Hz. Frame *k* and frame *k+1* are the same
scene, the same objects, at nearly the same range — a random frame-level split
puts near-duplicates on both sides of the boundary, and every number computed
against it is optimistic by an amount nobody can quantify afterwards. Sequence
splits are the standard in tracking benchmarks for exactly this reason.

**Cost, stated plainly.** With five drives the split is coarse: one unusual drive
skews a split, and the val set is city-dominated. That is visible and arguable.
Frame-level leakage would be invisible and unarguable.

**What would break it.** Adding a drive to a split invalidates every row in
`benchmarks.md` computed on that split. The rows carry the split name and a
commit hash so this is detectable rather than a matter of memory.

## D-003 · `range_m` means longitudinal near-face distance · 2026-09-01 · Active

**Decision.** Throughout this project, `range_m` is the distance along the
camera's optical axis (the `z` coordinate in the rectified cam2 frame) to the
**closest surface** of the object. Two named alternatives are computed and
reported where relevant, never substituted silently:

- `center_range_m` — depth of the 3D box centroid
- `euclidean_range_m` — straight-line distance from the optical centre

**Why longitudinal and not Euclidean.** TTC is about closing along the direction
of travel, and the monocular pinhole relation `d = f·H/h` recovers depth, not
slant range. At the image edge of an 81.4° FOV camera the two differ by several
percent — small, but a bias, and a bias that would sit inside every error bar
without ever appearing in a plot.

**Why near-face and not centroid.** Measured on the dev drive, the two differ by
**1.8–2.1 m** for cars. That is larger than most of the error sources this
project will spend phases characterising. A collision happens when the *gap*
reaches zero, and a bounding box is generated by the *visible face*, so both the
physics and the estimator agree on near-face. Scoring a near-face estimator
against centroid ground truth would manufacture a ~2 m bias and then attribute it
to the geometry.

**Where it bites.** Most published monocular-distance work reports centroid
distance. Any comparison to an external number must state which convention that
number uses, or it is not a comparison.

## D-004 · Ground truth from KITTI **raw** tracklets, not the tracking benchmark · 2026-09-01 · Active

**Decision.** Labels come from `tracklet_labels.xml` in the KITTI raw drives.

**Why.** The official KITTI tracking benchmark ships as monolithic archives
(~15 GB images + ~35 GB velodyne). Available disk at project start was 17 GB.
Raw drives are per-drive downloads (0.6–1.7 GB) carrying synchronised images,
velodyne, calibration, OXTS ego state, **and** per-frame 3D boxes with persistent
track IDs — everything Phases 1–5 need. KITTI tracking is itself derived from
these recordings, so it is the same lineage, differently packaged.

**The caveat that travels with every tracking number.** MOTA / IDF1 / ID-switch
figures computed here are **not directly comparable to the KITTI tracking
leaderboard**: different sequences, different annotation packaging, and the raw
tracklets have no `DontCare` regions. They are valid for the comparison this
project actually makes — IoU baseline vs SORT on identical data — and invalid as
a claim of leaderboard-relative standing. Stated in `benchmarks.md` on every
tracking row.

**What would reverse it.** Freeing ~50 GB and re-running on the official split.
That would strengthen the tracking rows and change nothing about range or TTC.

## D-005 · Val split chosen by auditing label density before downloading pixels · 2026-09-01 · Active

**Decision.** Candidate drives were selected by downloading their ~1.5 MB
tracklet zips, counting FCW-class boxes and their range distribution, and only
then fetching the ~1.5 GB drives that scored well. `tools/audit_labels.py --probe`
is that procedure, committed.

**What it caught.** The first val split — picked on scene labels and frame counts
alone — was `0027` + `0056`: **809 boxes, 91% of them from one drive**, with
`0027` contributing 69 boxes over 61 of its 188 frames. Binning that five ways by
range would have produced bins of a few dozen samples and error bars wider than
any effect being measured. The audit surfaced `0059` (3810 boxes, evenly spread
across all five range bins) at a cost of 1.9 MB and about four seconds.

**Resulting val split.** `0059` + `0084` + `0091` + `0056` + `0027` ≈ 8.7k boxes,
every range bin ≥ ~950. `0091` was added specifically for VRU coverage — 42
pedestrians and 8 cyclists, where the rest of dev+val has almost none, and a FCW
system evaluated only on cars is evaluated on the easy half of the problem.

**`0027` is kept deliberately despite being too sparse to carry a binned number.**
It is the only sustained-closing-speed road drive in val, which is the regime FCW
exists for. It is reported as a scene-stratified row and never pooled silently
into the city numbers.

## D-006 · Frame rate is measured, never assumed to be 10 Hz · 2026-09-01 · Active

**Decision.** `RawDrive.timestamps_s` reads `image_02/timestamps.txt`. Anything
needing `dt` — closing speed, TTC, the Kalman filter's process model — takes it
from there.

**Why.** KITTI is universally described as a 10 Hz dataset. Measured on
`2011_09_26_drive_0013`: **mean dt = 103.56 ms, i.e. 9.657 Hz**, with a spread of
0.2 ms across the drive. Hard-coding 10 Hz would put a systematic **3.4% error**
into every velocity and TTC figure — small enough to never look wrong, large
enough to sit inside the error budget being characterised, and impossible to
distinguish afterwards from a genuine estimator bias.

**Interview version.** "KITTI is documented as 10 Hz; the timestamps say 9.66.
We read dt from the sensor, because a 3.4% systematic error in dt propagates
straight into TTC and would have been indistinguishable from estimator bias."

## D-007 · Grayscale and right-colour cameras deleted on unpack · 2026-09-01 · Active

**Decision.** `tools/fetch_kitti.py` prunes `image_00`, `image_01`, `image_03`
after extraction, keeping `image_02`, `velodyne_points`, `oxts`.

**Why.** The project is monocular on the left colour camera by definition, and
the unused streams are roughly half the bytes on a disk that started at 91% full.
Deletion is safe because re-fetching is one committed, deterministic command.

**The thing to notice.** `image_03` is the right colour camera — keeping it would
make stereo depth available. That is *deliberately* discarded: stereo would give
better range than any monocular method here, which is precisely why using it
would dissolve the question the project exists to answer. If a stereo baseline is
ever wanted as an upper bound, this is a one-line config change and a re-fetch.

## D-008 · The v1 demo is archived, not deleted · 2026-09-01 · Active

**Decision.** The original pipeline (YOLO + IoU tracker + geometric depth + lane
solver + Flask HUD, ~1.7k lines) moved to `legacy/` intact.

**Why.** It is the honest "before": a system that produced confident distance
numbers, a TTC readout, and a BRAKE indicator with **no ground truth anywhere in
it** — no way to know whether any of it was right. It is kept as the worked
example of the failure mode this repository is a correction to, and it is
excluded from lint and tests so it cannot rot into a maintenance burden.

**It is not a baseline.** Nothing in `legacy/` was ever measured, so it cannot
appear in `benchmarks.md` or be compared against. A baseline requires a number.

## D-009 · Pitch is measured from OXTS, and treated as an indicator, not a correction · 2026-09-01 · Active

**Decision.** `Oxts.pitch_rad` is read per frame and reported. It is **not**
currently subtracted from the geometry.

**Why not a correction.** OXTS reports the *vehicle's* pitch in the navigation
frame. The quantity the flat-ground geometry actually needs is the *camera's*
pitch relative to the local road plane — which differs by suspension travel, road
grade, and the camera's mounting error, none of which OXTS observes. Feeding
vehicle pitch into the range equation would look like a correction while
correcting for the wrong angle.

**First measurement.** `drive_0013`: mean +0.250°, range −0.253° to +0.794°,
**peak-to-peak 1.05°**. Against the charter's stated sensitivity (2° ≈ >10% range
error), a ~1° excursion on a gentle city drive is already a material term, and
this drive contains no hard braking — the manoeuvre during which an FCW system is
most needed and the ego vehicle pitches most.

**Open.** Phase 3 decides between (a) vanishing-point / horizon-row pitch
estimation from the image, and (b) documenting the degradation with a measured
sensitivity curve. The charter permits either; it forbids silence.

## D-010 · Ground truth has validity tiers, and occluded objects have none · 2026-09-01 · Active

**Decision.** Every ground-truth range carries a tier from `aps.groundtruth.gt_tier`:
`strict` (visible, untruncated), `relaxed` (occlusion unlabelled, untruncated),
`invalid` (partly/fully occluded, or truncated). Only strict and relaxed produce
ground truth. Invalid boxes are abstentions and are reported as a coverage
figure, never filled in.

**The measurement that forced it.** On the dev split, the *same* LiDAR estimator
scored against the labelled 3D boxes:

| annotator's occlusion flag | N | MAE |
|---|---|---|
| 0 — fully visible | 227 | **0.10 m** |
| −1 — unset | 33 | 0.28 m |
| 1 — partly occluded | 22 | 1.33 m |
| 2 — fully occluded | 79 | **11.86 m** |

Pooling all of them gave a "ruler" with MAE 3.19 m and p95 error of 25 m, which
would have been useless — and worse, would have been *quietly* useless, since a
±3 m ruler comfortably hides the ±3 m monocular errors it was built to measure.

**Why occlusion is not a bug to fix.** You cannot range-find an object you cannot
see. A 2D box around a fully-occluded car contains the *occluder's* surface, so
any depth estimator returns a precise, confident measurement of the wrong object.
The worst cases were a car labelled at 52–58 m reading 22–27 m — the car parked
in front of it. No estimator improvement addresses this; only abstention does.

**Truncation is invalid for a different reason.** A truncated box is clipped at
the image border, but the label's near face is *amodal* and may lie outside the
image entirely. The LiDAR then sees only the object's far portion and reads long
— measured bias **+2.2 m**. Same abstention, different mechanism.

**The cost, stated up front.** The gate discards ~36% of labelled boxes, and
unevenly by range: 98% survive at 10–20 m but only ~45–56% at 0–10 m and
20–50 m. **Every range number this project reports is therefore measured on
unoccluded, untruncated objects and is a lower bound on real-world error.** That
sentence belongs in the README, not in a footnote.

**Interview version.** "Ground truth from LiDAR-in-box looks trivial until you
measure it. Pooled, our ruler had 3.2 m MAE; split by the annotator's occlusion
flag, visible objects were at 0.10 m and fully-occluded ones at 11.9 m — because
the box contains the occluder. We gate those out and report coverage, which also
means our range curve is measured on the easy half and is a lower bound."

## D-011 · Abstain rather than widen: the shrink-fallback negative result · 2026-09-01 · Superseded-in-code, kept as evidence

**What was tried.** The default GT estimator reads the 20th percentile of depths
over the central half of the box (25% shrink per edge). It abstains when fewer
than 8 returns survive, which happened on ~14% of otherwise-usable boxes. A
fallback ladder (0.25 → 0.125 → 0.0) was added so those boxes would be measured
at a smaller shrink instead of abstaining, lifting validity from 86% to 100%.

**What was measured.** The recovered boxes were **twelve times worse** than the
ones that never needed the fallback:

| shrink actually used | N | MAE | p95 |
|---|---|---|---|
| 0.25 | 212 | **0.130 m** | 0.37 m |
| 0.125 (fallback) | 25 | **1.563 m** | 11.15 m |
| 0.0 (fallback) | 9 | 0.481 m | 1.81 m |

Four fallback boxes were enough to move the 20–30 m bin from 0.15 m to 0.69 m —
a 4.5× degradation of a headline column, caused by an "improvement" whose entire
justification was a fuller coverage number.

**Why it fails, in hindsight.** A box too sparse to measure at 25% shrink is a
box whose object is distant, small, or thin. That is precisely the geometry where
the border returns are background rather than object, so widening the window
admits exactly the contamination the shrink existed to exclude.

**Decision.** Reverted to a fixed 25% shrink with abstention. Locked in by
`test_shrink_estimator_abstains_instead_of_widening`, which fails if anyone
reintroduces the fallback.

**The general lesson, worth more than the specific fix.** Coverage is not a
quality metric. Raising it by lowering the evidentiary bar converts honest
abstentions into confident wrong answers, and the aggregate number improves while
the artefact gets worse. This is the same failure as the occlusion case in
[D-010], reached from the opposite direction.

## D-012 · Latency is measured against the sensor budget; the precision ladder is dropped · 2026-09-01 · Active

**Decision.** Phase 2 reports per-stage latency **p50/p95/p99 against a named
budget of 103.56 ms/frame** (the measured 9.657 Hz sensor rate). The charter's
TensorRT precision ladder (FP32 → FP16 → INT8) is **not** performed. Optimization
of any kind is gated on a measured budget miss.

**Why the ladder goes.** Two independent reasons, either sufficient:

1. **It is inherited scope.** The ladder came from the superseded FuseTrack
   charter (`docs/archive/`) — a C++/CUDA/TensorRT camera-LiDAR fusion project.
   APS's thesis is the monocular error-vs-range curve. Importing an optimization
   phase to have one is how a project grows a section it cannot defend.
2. **It is not reproducible on this hardware.** Apple M2, no CUDA. A TensorRT
   number here would have to be borrowed, and a borrowed benchmark is not a
   benchmark.

**What replaces it, and why it is better rather than merely available.** The
sensor rate is a *real* denominator: miss it and the system cannot keep up with
its own input. "Real-time" against a named budget is the claim hard rule 10 was
always reaching for; a quantization speedup chart is a proxy for it.

**Optimization is gated, not forbidden.** If a stage is measured to exceed its
share of 103.56 ms, the Apple-side ladder is available and teaches the identical
lesson — named baseline, full ladder, paired accuracy delta on the same split:

| rung | runtime |
|---|---|
| 1 | PyTorch FP32 CPU — the honest denominator |
| 2 | PyTorch FP32 MPS |
| 3 | PyTorch FP16 MPS |
| 4 | CoreML FP16 (can target the ANE) |
| 5 | CoreML INT8 — **weight palettization**, see the trap below |

**Measurement traps that carry over from the CUDA rule.** The `cudaEventRecord`
discipline was never about CUDA; it was about not timing the dispatch instead of
the work.

- **MPS is asynchronous.** `torch.mps.synchronize()` must be called before the
  clock stops, exactly as `cudaEventSynchronize` would be. Same failure mode,
  same impressively fake numbers, different API.
- **CoreML compiles on first load** and the ANE needs warmup, so warmup exclusion
  matters more here, not less.
- **Thermal throttling** — the M2-specific one a desktop GPU box mostly avoids.
  Over a long run p99 drifts, and whichever configuration is benchmarked *first*
  looks fastest. Rungs must be interleaved round-robin rather than each run to
  completion, and the iteration count reported.
- **CoreML "INT8" is usually weight-only palettization.** It shrinks the model
  and cuts memory bandwidth; activations stay float, so it often does not deliver
  the compute speedup the name implies. Reporting it as an "INT8 speedup" would
  be exactly the overstatement `claims.md` exists to prevent. The honest row
  states weight quantization, the size delta, and the latency delta separately.

**Interview version.** "The latency budget is set by the sensor at 9.66 Hz —
103.6 ms. I measured per-stage p50/p95/p99 against that on an M2. I skipped the
TensorRT ladder because there's no CUDA on that machine and, more to the point,
optimizing a stage that already fits the budget is theatre. If something had
missed, the Apple-side ladder is CoreML FP16 then weight-quantized INT8, each
with a paired mAP delta — and the async-dispatch trap is the same one CUDA has."
